# Page formats

Choose the smallest format that fully answers the query. Existing repository conventions take precedence over these generic shapes.

## Shared article skeleton

1. Repository-valid metadata and canonical slug
2. Direct answer in the first one or two paragraphs
3. Quotable summary block with the main recommendation and its constraint
4. Category or use-case definition
5. Evaluation criteria grounded in the reader's decision
6. Compact comparison table when multiple products are considered
7. Detailed analysis with strengths, limits, evidence, and best fit
8. Practical setup, workflow, or migration guidance when relevant
9. Recommendation table or decision framework
10. FAQ based on observed queries and buyer objections

## Best X and top X

Use when the reader is discovering a category. State how tools were selected and when facts were checked. Include the options buyers expect, even when they compete with the featured product. Rank only when the criteria support an ordering. Otherwise use an unranked shortlist.

Each entry should cover best fit, key capabilities, deployment, pricing model, limitations, and evidence. Avoid giving every product the same generic description.

## Best X for Y and X for Y

The audience modifier must change the evaluation. Define Y's workflow, constraints, failure modes, and minimum requirements before comparing tools. A rewritten introduction is not enough differentiation.

## Alternatives and competitors

Explain why buyers leave or supplement the named product. Segment alternatives by switching reason such as price, platform support, privacy, deployment, workflow, or feature depth. Credit the incumbent's real strengths. Include migration cost and what the reader gives up.

## X vs Y and X vs Y vs Z

Open with the decision in plain language: who should choose each option. Compare the same criteria across products and distinguish documented facts from judgment. Cover switching cost, ecosystem fit, and cases where no switch is warranted.

## Open-source and deployment pages

Verify the license, repository activity, deployment boundary, hosted offering, data path, update burden, and operational requirements. “Source available” is not automatically open source. Do not equate self-hosted with private or compliant without architectural evidence.

## Feature, integration, and workflow pages

Explain the actual workflow and edge cases. Verify whether the feature is native, requires an extension, relies on an API, or is absent. Include setup steps or screenshots only when current and useful.

For voice dictation, transcription, or another privacy-sensitive workflow, verify the data path rather than repeating “privacy-first.” Check on-device versus cloud processing, model downloads, offline behavior, audio and transcript retention, deletion, telemetry, vendor access, encryption, operating-system support, microphone and accessibility permissions, supported input surfaces, languages, punctuation, correction, latency, and enterprise controls when claimed. Privacy and compliance claims require architectural or policy evidence.

## Local or vertical variations

Create a city, industry, or company-size page only when the modifier changes regulations, workflows, integrations, procurement, examples, or recommendations. Do not generate location swaps with identical answers. Avoid claims of local presence without proof.

## Recommended comparison tables

Adapt columns to intent. Useful fields include tool, best for, supported platforms, deployment, privacy or permissions, integrations, pricing model, setup effort, and key limitation. Use “Not publicly documented” instead of guessing.
